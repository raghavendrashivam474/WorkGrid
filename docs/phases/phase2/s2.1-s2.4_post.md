## 1. Executive Summary

Phase 2 transformed WorkGrid from a CRUD application managing independent Employee and Asset entities into a coherent operational asset-management system. The central relationship — Employee ↔ Assignment ↔ Asset — is now fully functional with transactional consistency, domain-enforced invariants, relational detail views, search/filter capabilities, and a live operational dashboard. All data remains local-first on SQLite with no backend dependency.

**Final state:** 0 build errors, 0 build warnings, 44 tests passing across 3 test projects, Android target builds clean.

## 2. Sprint-by-Sprint Implementation Detail

### 2.1 Sprint S2.1 — Assignment Workflow

**Objective:** Build the first real business workflow: assign an available asset to an employee, return it, and maintain consistency across all three entities.

**What was implemented:**

- **Domain strengthening (`Asset.cs`):** `MarkAssigned()` was tightened to only allow transitions from `Available` (previously it only blocked `Retired`, meaning a `Maintenance` or already-`Assigned` asset could be double-assigned). `MarkAvailable()` was tightened to only allow transitions from `Assigned` or `Maintenance`.

- **Assignment service layer:** Created `IAssignmentService` (contract) and `AssignmentService` (implementation) to coordinate multi-entity writes. The `AssignAssetAsync` method validates employee existence, asset existence, checks for duplicate active assignments, calls `asset.MarkAssigned()` (domain transition), creates the `Assignment` entity, and persists both changes inside an EF Core database transaction. `ReturnAssetAsync` follows the same pattern in reverse.

- **Assignment UI:** Created `AssignmentListPage` (displays all assignments with resolved employee names and asset tags via in-memory join) and `AssignmentDetailPage` (dual-mode: creation with employee/asset pickers filtered to available assets, and detail view with return button for active assignments).

- **Shell integration:** Added "Assignments" flyout item, registered `assignment-detail` route, wired all ViewModels and Views into DI.

- **Status color converter:** Created `ActiveStatusColorConverter` for visual differentiation of active vs. returned assignments in the list.

**Problems faced and mitigations:**

| # | Problem | Root Cause | Mitigation |
|---|---------|-----------|------------|
| 1 | `AssignmentService` initially placed in `WorkGrid.App/Services/` | Seemed natural since it's "application logic," but `WorkGrid.Infrastructure.Tests` could not reference `WorkGrid.App` without creating a circular/layering violation | Relocated `IAssignmentService` to `WorkGrid.Domain.Contracts` and `AssignmentService` to `WorkGrid.Infrastructure.Services`. The service depends on `WorkGridDbContext` for transactions, so Infrastructure is the correct home. DI registration moved to `ServiceCollectionExtensions.AddInfrastructure()`. |
| 2 | `SQLite does not support expressions of type 'DateTimeOffset' in ORDER BY clauses` | EF Core's SQLite provider cannot translate `DateTimeOffset` to a sortable SQL expression. The existing `AssignmentRepository` used `.OrderByDescending(a => a.AssignedAt)` which failed at runtime. | Added ISO 8601 string value converters in `AssignmentConfiguration.cs` using `HasConversion(v => v.ToString("o", CultureInfo.InvariantCulture), v => DateTimeOffset.Parse(v, CultureInfo.InvariantCulture))`. This makes SQLite store dates as lexicographically sortable strings while the domain continues to work with `DateTimeOffset`. |
| 3 | PowerShell string escaping errors when injecting C#/XAML containing embedded quotes | `-replace` operations with `\"` inside double-quoted PowerShell strings caused parser errors | Switched to single-quoted verbatim here-strings (`@'...'@`) for all file content and used backtick escaping for inline replacements. |

**Tests added:** 5 workflow integration tests in `AssignmentWorkflowTests.cs` covering successful assign, duplicate assign rejection, maintenance-state assign rejection, successful return, and double-return rejection. 2 new domain tests in `AssetTests.cs` for tightened state transitions.

**Tag:** `vS2.1`

### 2.2 Sprint S2.2 — Search, Filters & Dashboard

**Objective:** Make WorkGrid useful for daily operational work, not just data entry.

**What was implemented:**

- **Employee search (`EmployeeListViewModel.cs`):** Added a `SearchText` property bound to a `SearchBar`. Filtering is performed in-memory against the full employee list across `Name`, `EmployeeCode`, `Email`, and `Department` using `StringComparison.OrdinalIgnoreCase`. No database-level full-text search was introduced — the dataset is small enough for client-side filtering.

- **Asset search and status filtering (`AssetListViewModel.cs`):** Added `SearchText` (searches `AssetTag`, `Name`, `SerialNumber`, `AssetType`) and `SelectedFilter` (Picker bound to `All`, `Available`, `Assigned`, `Maintenance`, `Retired`). Both filters compose: the status filter is applied first, then the text search narrows further. Empty states provide contextual messages ("No assets match 'X'" vs. "No assets with status 'Maintenance'").

- **Employee relational view (`EmployeeDetailViewModel.cs` & `EmployeeDetailPage.xaml`):** In edit mode, the employee detail page now shows two sections below the form fields: "Currently Assigned Assets" (active assignments with asset tag, name, and assignment date) and "Assignment History" (returned assignments with period dates). Data is loaded via `IAssignmentRepository.GetByEmployeeIdAsync()` and joined in-memory with the asset catalog.

- **Asset relational view (`AssetDetailViewModel.cs` & `AssetDetailPage.xaml`):** In edit mode, the asset detail page now shows a "Current Holder" card (employee name, code, holding-since date) when the asset is assigned, plus a full "Assignment History" list showing all past and present holders with status badges.

- **Operational dashboard (`HomeViewModel.cs` & `HomePage.xaml`):** Replaced the Phase 1 placeholder with a live metrics dashboard. On appearance, `LoadDashboardAsync()` queries all three repositories and computes: Total Employees, Total Assets, Available/Assigned/Maintenance/Retired counts, and Active Assignment count. The page supports pull-to-refresh. All numbers come from real SQLite queries — nothing is hard-coded.

**Problems faced and mitigations:**

| # | Problem | Root Cause | Mitigation |
|---|---------|-----------|------------|
| 1 | No significant technical blockers | The patterns established in S2.1 (repository queries, ViewModelBase, Shell routing) scaled cleanly | Followed existing conventions exactly. Used `MainThread.BeginInvokeOnMainThread()` for collection updates triggered from `Task.Run` background loads. |

**Tests:** No new tests required — S2.2 was purely presentational. Existing test suite remained green.

**Tag:** `vS2.2`

### 2.3 Sprint S2.3 — Business Rules & Validation Hardening

**Objective:** Make invalid business states difficult or impossible to create through the domain layer.

**What was implemented:**

- **Asset lifecycle hardening (`Asset.cs`):** Added two new guards:
  - `MarkMaintenance()` now throws if `Status == Assigned` with the message "Cannot place an assigned asset into maintenance. Return the asset first."
  - `Retire()` now throws if `Status == Assigned` with the message "Cannot retire an assigned asset. Return the asset first."
  
  This ensures the complete state machine is:
  ```
  Available → Assigned → Available (return)
  Available → Maintenance → Available
  Available → Retired (terminal)
  Maintenance → Retired
  ```
  An asset involved in an active assignment **cannot** enter Maintenance or Retired without first being returned. This is a deliberate business decision documented here.

- **Test coverage:** Added `MarkMaintenance_OnAssignedAsset_ThrowsDomainValidationException` and `Retire_OnAssignedAsset_ThrowsDomainValidationException` to `AssetTests.cs`.

**Problems faced and mitigations:**

| # | Problem | Root Cause | Mitigation |
|---|---------|-----------|------------|
| 1 | `PersistenceTests.AssetRepository_AddAndCheckLifecyclePersistence_WorksCorrectly` failed | The Phase 1 test called `asset.MarkAssigned()` then `asset.Retire()` directly — a sequence that was valid under the old lax rules but is now correctly rejected by the hardened domain | Updated the test to follow the proper lifecycle: `MarkAssigned()` → `MarkAvailable()` → `Retire()`. This is the correct business flow and the test now documents the expected sequence. |

**Design decision documented:** The question "Can an asset currently involved in an active assignment enter Maintenance or Retired?" was answered explicitly: **No.** The asset must be returned first. This prevents the inconsistent state where an assignment is Active but the asset is in Maintenance or Retired.

**Tag:** `vS2.3`

### 2.4 Sprint S2.4 — Local-First Operational Hardening

**Objective:** Ensure the standalone local application is dependable across restarts, interruptions, and repeated use.

**What was implemented:**

- **Code quality cleanup:** Eliminated all CA1304, CA1311, and CA1862 warnings in the Infrastructure layer:
  - `AssetRepository.ExistsByTagAsync()`: Replaced `.ToUpper()` with `.ToUpper(CultureInfo.InvariantCulture)` and moved normalization outside the LINQ expression.
  - `EmployeeRepository.ExistsByCodeAsync()`: Same treatment — normalized the code before the query and used direct string comparison inside the expression to avoid EF Core translation issues.
  - Final build: **0 warnings, 0 errors** (down from 37 warnings at the start of Phase 2).

- **Simulated restart persistence test (`LocalLifecyclePersistenceTests.cs`):** Created a comprehensive integration test that simulates four app sessions using separate `DbContext` instances over the same SQLite connection:
  1. Session 1: Create employee + asset, assign asset.
  2. Session 2 (simulated restart): Verify asset is `Assigned` and assignment is `Active`.
  3. Session 3: Return the asset.
  4. Session 4 (second restart): Verify asset is `Available`, assignment is `Returned` with `ReturnedAt` populated.
  
  This proves that all workflow state survives context disposal and re-creation, which is the closest in-memory analogue to actual app restarts.

- **ViewModel loading guards:** All list ViewModels already had `if (IsLoading) return;` guards from Phase 1. Detail ViewModels use `IsBusy` flags. No additional concurrency framework was needed.

- **Empty state handling:** All list pages and the dashboard handle empty databases gracefully — no null-reference crashes, no fake seed data.

**Problems faced and mitigations:**

| # | Problem | Root Cause | Mitigation |
|---|---------|-----------|------------|
| 1 | EmployeeRepository still had CA warnings after initial cleanup | The LINQ expression `e.EmployeeCode.ToUpper() == normalizedCode` used `.ToUpper()` inside the expression tree, which EF Core translates but analyzers flag | Removed the in-expression `.ToUpper()` call entirely. Since the domain constructor already normalizes `EmployeeCode` via `.Trim()` (and the repository normalizes the search input), direct equality comparison is sufficient and warning-free. |

**Tag:** `vS2.4` and `v2.0`

## 3. Architecture Summary

The architecture remains consistent with the Phase 1 baseline. One structural addition was made:

```
WorkGrid.Domain
  └── Contracts/
      └── IAssignmentService.cs    ← NEW (service contract)

WorkGrid.Infrastructure
  ├── Services/
  │   └── AssignmentService.cs     ← NEW (transactional implementation)
  ├── Repositories/
  ├── Persistence/
  └── DependencyInjection/

WorkGrid.App
  ├── ViewModels/
  │   ├── Assignments/             ← NEW
  │   └── Common/                  ← NEW (shared DTOs)
  ├── Views/
  │   └── Assignments/             ← NEW
  ├── Converters/                  ← NEW (ActiveStatusColorConverter)
  └── Services/                    ← REMOVED (relocated to Infrastructure)
```

**Key architectural decision (ADR-worthy):** The `AssignmentService` was moved from `WorkGrid.App` to `WorkGrid.Infrastructure` because it directly depends on `WorkGridDbContext` for transaction management. The contract (`IAssignmentService`) lives in `WorkGrid.Domain.Contracts` so that any layer can depend on it without referencing Infrastructure directly. This follows the existing pattern where `IAssignmentRepository` is in Domain and `AssignmentRepository` is in Infrastructure.

## 7. Known Technical Debt & Recommendations for Phase 3

1. **Test naming convention (CA1707):** All 44 test methods use underscore-separated names (e.g., `Constructor_WithValidData_CreatesAsset`). This triggers CA1707 warnings. Recommend suppressing CA1707 in test projects via `.editorconfig` or `#pragma` — this is standard practice for xUnit test naming.

2. **ViewModel `Task.Run` fire-and-forget:** Detail ViewModels use `Task.Run(LoadXxxAsync)` in property setters triggered by Shell query parameters. This works but swallows exceptions silently. Consider migrating to `async void OnAppearing()` patterns or a proper initialization lifecycle in Phase 3.

3. **No database migration strategy:** The app uses `EnsureCreated()` which works for fresh installs but will not handle schema changes across versions. Phase 3 (or Phase 4 with a backend) should introduce EF Core Migrations.

4. **In-memory joins for relational views:** Employee and Asset detail pages load all assignments + all related entities and join in-memory. This is fine for the current scale but should be revisited if the dataset grows beyond a few thousand records.
