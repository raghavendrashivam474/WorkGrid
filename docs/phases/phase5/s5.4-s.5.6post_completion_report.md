## 2. What Was Built

### 2.1 S5.4 — Sync Metadata & Change Capture

**Goal:** make the synchronization model persistent and operational — device identity, local sequence generation, change history, tombstones, and checkpoints must all survive restart, and must commit atomically with the domain mutation that caused them.

**What landed:**

1. Three persistent EF entities in `src/WorkGrid.Infrastructure/Persistence/`:
   - `SyncDeviceRecord` → table `SyncDevices` (one row per database, the stable local replica identity)
   - `SyncChangeRecord` → table `SyncChanges` (local change log + tombstone store)
   - `SyncCheckpointRecord` → table `SyncCheckpoints` (one row per known remote replica)
2. Three EF `IEntityTypeConfiguration<T>` classes in `Persistence/Configurations/`, each with explicit indexes:
   - `(OriginatingDeviceId, SequenceNumber)` — for the MAX query that computes the next sequence
   - `(ObjectType, ObjectId)` — for per-object history lookups
   - `(OriginatingDeviceId, ObjectType, ObjectId)` — for manifest building
3. A new EF migration `20261005175702_AddSyncMetadata` that is strictly additive — existing tables are untouched, so a v1.0.0 database migrates forward cleanly.
4. `WorkGridDbContext` modified to:
   - Expose `DbSet<SyncDeviceRecord>`, `DbSet<SyncChangeRecord>`, `DbSet<SyncCheckpointRecord>`
   - Override both `SaveChangesAsync` and `SaveChanges`
   - Walk the ChangeTracker, filter to `Employee`/`Asset`/`Assignment` entries, and emit a `SyncChangeRecord` for each one **before** calling `base.SaveChangesAsync()`, so the domain row and the sync row commit in a single SQLite transaction

**What was deliberately NOT changed:**

- Zero modifications to `Employee`, `Asset`, `Assignment`, or `User` domain entities (§46)
- Zero modifications to `EmployeeRepository`, `AssetRepository`, `AssignmentRepository`, `UserRepository`, or `AssignmentService`
- No `SyncBaseEntity`, no domain events, no new interfaces imposed on domain types
- `User` sync is still deferred (§5)

### 2.2 S5.5 — Sync Engine & Local Reconciliation

**Goal:** build a transport-independent engine that can generate a manifest, select the right local changes to send, apply incoming remote changes safely, and update checkpoints — with no HTTP, no sockets, and no cloud involvement.

**What landed:**

1. `ISyncEngine` interface in `src/WorkGrid.Domain/Sync/ISyncEngine.cs` — three methods: `GenerateLocalManifestAsync`, `SelectLocalChangesAsync`, `ApplyRemoteChangesAsync`. The interface lives in Domain so Infrastructure/Api can depend on it without introducing an outward dependency.
2. `SyncManifestBuilder` in `src/WorkGrid.Infrastructure/Sync/` — reads active entities, computes a SHA-256 state hash from `JsonSerializer.Serialize(entity)`, looks up each entity's latest `SyncChangeRecord` to derive its `SyncVersion`, and emits tombstone summaries (hash `"TOMBSTONE"`) for objects whose latest change is `Delete`.
3. `SyncEngine` in `src/WorkGrid.Infrastructure/Sync/` — the orchestrator. Key behaviors:
   - **Reuses the existing `SyncReconciler`** (§26) — does not duplicate reconciliation logic
   - **Change selection** filters by remote's known version per object (skips what the remote already has)
   - **Application order**: Employees and Assets first, Assignments second (§28 dependency awareness)
   - **Integrity verification**: calls `SyncChange.VerifyIntegrity()` on every inbound change before processing
   - **Idempotency**: checks `SyncChangeRecords` for the incoming `ChangeId` before applying anything (§29)
   - **Domain-respecting application**: deserializes payloads into private DTOs, then invokes the real domain constructors and methods (`new Employee(...)`, `asset.UpdateDetails(...)`, `assignment.CompleteReturn(...)`) rather than bypassing invariants
   - **Dependency validation**: before applying an incoming Assignment, verifies the referenced Employee and Asset exist locally — otherwise throws `DomainValidationException` (§28)
   - **Checkpoint progression**: updates `SyncCheckpointRecord.LastAppliedSequenceNumber` only after successful application, and only forward (§30)

### 2.3 S5.6 — Cloud Relay Foundation

**Goal:** introduce the first real transport without turning the cloud into the authoritative database and without polluting the existing CRUD API (§35).

**What landed:**

1. **Separate `/api/sync/*` endpoints** in `src/WorkGrid.Api/Controllers/SyncController.cs`:
   - `POST /api/sync/session` — session acknowledgement
   - `POST /api/sync/manifest` + `GET /api/sync/manifest/{deviceId}` — manifest upload/retrieval
   - `POST /api/sync/envelope` — push a `SyncEnvelope` of changes targeted at another device
   - `GET /api/sync/pending/{deviceId}` — poll incoming envelopes
   - `POST /api/sync/ack` — acknowledge an envelope so it's removed from the queue
   - All endpoints require `[Authorize]` — the existing JWT infrastructure is reused unchanged
2. `RelayCoordinator` in `src/WorkGrid.Api/Sync/` — a `ConcurrentDictionary`-backed, in-memory message router. It stores the latest manifest per device, maintains a per-recipient envelope queue, and deduplicates by `EnvelopeId`. It is explicitly **not** a database, **not** a domain engine, and **not** a replacement for `SyncEngine` (§37).
3. Protocol transfer objects in `src/WorkGrid.Infrastructure/Remote/Sync/SyncProtocolModels.cs`:
   `SyncSessionRequest`, `SyncSessionResponse`, `SyncManifestEnvelope`, `SyncEnvelope`, `SyncAckRequest`
4. Client-side abstraction `ISyncTransport` and HTTP implementation `HttpSyncRelayTransport` — the sync engine depends on the abstraction, so swapping in a different transport (Direct P2P, durable cloud replica) later requires no change to `SyncEngine` (§34).
5. `SyncObjectKeyJsonConverter` — fixes System.Text.Json's inability to serialize complex dictionary keys (details in §4.3 below). Registered globally in `Program.cs` via `AddJsonOptions`.

## 3. Design Decisions

### 3.1 Change Capture Strategy — SaveChanges Interception (Option B)

The brief laid out four options in §16 (explicit repository recording, SaveChanges interception, domain events, database triggers). I evaluated them against the existing architecture:

| Option | Atomicity | Repo changes | Entity changes | Verdict |
|---|---|---|---|---|
| A — Explicit recording in each repo | Good (same `SaveChanges`) | Modify all 3 repos | None | Spreads sync logic across repos; brittle if a new repo is ever added |
| **B — SaveChanges interception** | **Excellent (same transaction)** | **Zero** | **Zero** | **Chosen** |
| C — Domain events | Risky (would require event dispatch inside domain) | Modify services | Modify entities | Violates §46 (no `SyncBaseEntity`); couples domain to sync |
| D — DB triggers | Excellent | Zero | Zero | Fragile, SQLite-specific, can't inspect operation context cleanly |

**Why B won:**
- Zero modifications to repositories or entities — §46 guardrail honored
- Atomic by construction: sync records are added to the ChangeTracker before `base.SaveChangesAsync()`, so both commit in the same SQLite transaction
- Tombstones are automatic — `EntityState.Deleted` entries still expose their `Id` via `entry.Property("Id").CurrentValue` before the row is removed
- One file touched (`WorkGridDbContext.cs`), one override point

This is not a material architectural change per §17/§45 (no dependency direction change, no domain modification, no new patterns), so it did not require a stop-the-world ADR escalation. ADR-0012 was still written to document the decision.

### 3.2 Payload Serialization

Each `SyncChangeRecord` payload is `JsonSerializer.Serialize(entry.CurrentValues.ToObject())`. This gives us a stable, structural snapshot of the entity at mutation time without any entity-side changes. The `PayloadHash` is SHA-256 over the UTF-8 bytes, matching the existing `SyncChange.CalculateHash` algorithm in Domain so `VerifyIntegrity()` works end-to-end.

### 3.3 Manifest State Hashing

For active entities, `SyncManifestBuilder` computes `SHA256(JsonSerializer.Serialize(entity))`. For tombstones, the hash is the literal string `"TOMBSTONE"`. The reconciler then correctly identifies divergence between a replica that still has an object and one that has tombstoned it — the hashes differ, so the result is `PotentialConflict` or `NewerLocally`/`NewerRemotely` based on versions.

### 3.4 Reconciler Reuse

`SyncReconciler.Reconcile(local, remote)` from S5.3 is called verbatim. The engine does not reimplement reconciliation — it only orchestrates it. This preserves §26's requirement that the reconciler remains the canonical reconciliation decision mechanism and keeps the pure/deterministic/side-effect-free property intact.

### 3.5 Relay as Transport, Not Store

`RelayCoordinator` deliberately does not persist. It is an in-memory message router. If the API process restarts, pending envelopes are lost — this is acceptable because the client-side `SyncEngine` holds the authoritative change log in SQLite and will re-send on the next sync cycle. The relay is a transport (§37), not a database. Durable cloud replica (Path C) is explicitly deferred (§57).

### 3.6 Device Identity ≠ User Identity

The device identity (`SyncDevices.DeviceId`) is a GUID generated per database, not derived from the authenticated user (§13). This is correct because one user can operate multiple devices, and reusing the user ID would collapse their replicas into a single logical device.

## 4. Problems Encountered and Mitigations

### 4.1 Problem — Missing `Microsoft.EntityFrameworkCore.Design` in Startup Project

**Symptom:** First attempt at `dotnet ef migrations add AddSyncMetadata --startup-project src/WorkGrid.Api` failed with:
> Your startup project 'WorkGrid.Api' doesn't reference Microsoft.EntityFrameworkCore.Design.

**Analysis:** The `WorkGrid.Infrastructure` project already contained a `WorkGridDbContextFactory` and the `Microsoft.EntityFrameworkCore.Design` package reference. The API project did not.

**Mitigation:** Rather than add a design-time package reference to `WorkGrid.Api` (which would mean shipping EF tooling with the production API), I pointed both `--project` and `--startup-project` at `WorkGrid.Infrastructure` and let the existing `WorkGridDbContextFactory` handle design-time context creation.

**Result:** Migration generated cleanly, no production project pollution.

### 4.2 Problem — `CA1861` Warnings in Generated Migration

**Symptom:** The EF-generated migration file emitted three `CA1861: Prefer 'static readonly' fields over constant array arguments` warnings on the index column arrays. Per §48, every sprint must finish with zero warnings.

**Analysis:** This is EF Core's generated code — we don't want to modify generator output or suppress the analyzer solution-wide.

**Mitigation:** Prepended a single `#pragma warning disable CA1861` to the top of the generated migration file. Scoped suppression, confined to generated code, no analyzer config changes.

**Result:** 0 warnings, 0 errors.

### 4.3 Problem — `CA1001` Warning on `HttpSyncRelayTransport`

**Symptom:** The transport class held an `HttpClient` field but did not implement `IDisposable`.

**Mitigation:** Added `IDisposable` with a disposal flag; `Dispose()` now disposes the underlying `HttpClient` exactly once.

**Result:** 0 warnings.

### 4.4 Problem — `System.Text.Json` Cannot Serialize `SyncObjectKey` as Dictionary Key

**Symptom:** The two-device relay integration test failed during the manifest POST step:
> `The type 'WorkGrid.Domain.Sync.SyncObjectKey' is not a supported dictionary key using converter of type 'SmallObjectWithParameterizedConstructorConverter'. The unsupported member type is located on type 'SyncObjectSummary'. Path: $.Manifest.Objects.`

**Analysis:** `SyncManifest` holds `IReadOnlyDictionary<SyncObjectKey, SyncObjectSummary>`. JSON object keys must be strings. STJ supports primitive and enum keys out of the box but refuses complex record keys without a converter — and attempting to use the parameterized-constructor converter as a property-name writer explicitly throws.

I had two options:
- (a) introduce a wire DTO in Infrastructure that converts `SyncManifest.Objects` into `Dictionary<string, SyncObjectSummary>` for transport
- (b) write a `JsonConverter<SyncObjectKey>` that overrides `WriteAsPropertyName`/`ReadAsPropertyName` to format keys as `"{Type}:{Id}"`

**Mitigation:** Chose (b). It is one 50-line file in `WorkGrid.Infrastructure.Remote.Sync/SyncObjectKeyJsonConverter.cs`, keeps the Domain `SyncManifest` type unchanged (no Domain pollution), and is registered once in `Program.cs` via `AddJsonOptions` on the server and in a `JsonSerializerOptions` singleton on the client (`HttpSyncRelayTransport` and the integration test fixture).

**Result:** Round-trip serialization works; the two-device relay test converges cleanly. The chosen wire format (`"Employee:guid"`) is debuggable in raw JSON and reversible via `Enum.TryParse` + `Guid.TryParse`.

### 4.5 Problem — Test Project Missing a Using Directive

**Symptom:** `SyncRelayIntegrationTests.cs` failed to compile with `CS0246: The type or namespace name 'ITokenService' could not be found`.

**Analysis:** `ITokenService` lives in `WorkGrid.Domain.Contracts`, which the test project references but whose namespace was not imported.

**Mitigation:** Added `using WorkGrid.Domain.Contracts;`. No csproj changes needed — the reference chain was already correct.

**Result:** Clean compile.

### 4.6 Non-Problem — Preserving Dependency Direction

Every new type was placed with explicit attention to §3's dependency direction:
- `ISyncEngine` → Domain (interface only)
- `SyncEngine`, `SyncManifestBuilder` → Infrastructure (implementations with EF Core access)
- `SyncController`, `RelayCoordinator` → Api
- `ISyncTransport`, `HttpSyncRelayTransport`, `SyncObjectKeyJsonConverter` → Infrastructure
- All protocol DTOs (`SyncEnvelope` etc.) → Infrastructure (not Domain — they are wire concerns)

Domain still depends on nothing. Infrastructure still depends only on Domain. API still depends on both. No circular reference, no inversion, no leak.

## 7. Known Limitations and Explicit Deferrals

1. **`RelayCoordinator` is not durable.** API process restart drops the pending-envelope queue. This is intentional — clients will re-send on next sync — but it will need to evolve when we introduce the durable cloud replica (Path C).
2. **Relay authorization is session-level only.** The brief (§39) explicitly flagged that user-authentication ≠ device-authorization, and that a full device-registration model may require follow-up work. The current implementation uses the existing JWT and treats any authenticated principal as able to use the relay. A device-to-user binding registry is a candidate for a follow-up ADR.
3. **No tombstone compaction.** Per §19, retention policy was out of scope. The `SyncChanges` table grows monotonically. First real-world soak test should inform compaction policy.
4. **Device ID generation on first mutation.** A fresh database with no mutations has no device identity. This is deliberate (identity is created lazily inside the same `SaveChanges` transaction as the first mutation) but worth noting if a future feature needs to know the device identity before any user action.
5. **`AssignmentService` was intentionally not migrated to an explicit transaction.** It still performs its two `UpdateAsync` calls as separate `SaveChanges` operations — meaning each one gets its own sync record and its own atomic commit, but the business operation as a whole is not transactionally atomic. This matches v1.0.0 behavior and was not in scope for S5.4. If atomic business operations become a requirement, a Unit-of-Work introduction would be its own ADR.
