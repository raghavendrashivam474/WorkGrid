## 3. Implementation Approach

### 3.1 Methodology

Implementation was carried out in small, individually-verified blocks. After every meaningful code change, the full solution was built and all tests executed before proceeding. This was a deliberate choice to catch regressions immediately rather than at sprint end.

Sequence followed:

1. **Baseline verification** — confirmed `v3.0` builds clean and all 88 tests pass before any changes.
2. **Architecture inspection** — read composition root, DI extension, domain contracts, representative ViewModel, and both `.csproj` files before designing anything.
3. **Architecture proposal** — explicit written decisions (see §4) on where each component lives, before writing code.
4. **Core types first** — created value/model types (`ConnectionState`, `RemoteErrorKind`, `RemoteResult`, `RemoteEndpoint`) and verified they compiled cleanly before introducing the client.
5. **Client implementation** — introduced `IRemoteClient` and `RemoteClient`, then immediately cleaned warnings before proceeding.
6. **DI integration** — extended `AddInfrastructure(...)` with an **optional** `RemoteEndpoint? remoteEndpoint = null` parameter to preserve backward compatibility with the existing `MauiProgram.cs` call site.
7. **Test coverage** — 17 unit tests written using a custom `HttpMessageHandler` to enable fully deterministic testing without a live network.
8. **Android verification** — built `WorkGrid.App` for `net8.0-android` to confirm no MAUI regression.
9. **Documentation** — ADR authored and phase closeout report drafted.
10. **Commit and tag** — conventional commit, then `vS4.1` tag.

### 3.2 Working Branch Strategy

A dedicated branch `feature/S4.1-remote-boundary` was created from `v3.0`. This ensured the tag `v3.0` and `main` remained untouched until the sprint was verifiably complete.

## 4. Architectural Decisions

Before writing any code, an explicit architecture proposal was recorded answering the questions posed in the brief:

| Question | Decision |
|---|---|
| Where does remote communication live? | `WorkGrid.Infrastructure/Remote/` — new folder, peer to `Persistence/` and `Services/`. |
| Where does connectivity state live? | Exposed by `IRemoteClient.State` and `IRemoteClient.StateChanged`. No global state singleton was introduced. |
| How is endpoint configuration represented? | Immutable `RemoteEndpoint` record. No hardcoded production URLs, no embedded credentials. |
| How does the App consume it? | Through the existing DI extension `AddInfrastructure(...)`. Existing MAUI composition root remains one-line. |
| How does this remain reusable? | Interface-based (`IRemoteClient`), no business logic embedded, transport errors only. |
| How does this preserve local-first? | No existing ViewModel depends on `IRemoteClient`. If the endpoint is unreachable, all local SQLite workflows continue unchanged. |

**Dependency direction preserved unchanged.** The Phase 0 rule (`App → Infrastructure`, `App → Domain`, `Infrastructure → Domain`, `Domain → nothing`) was not modified. No domain contracts were added. No projects were renamed or moved.

This decision is recorded formally in **ADR 0006 — Remote Boundary Foundation**.

### 6.4 Problem: 4 Compiler Warnings after `RemoteClient` Implementation

**Symptom:**
Initial build of `RemoteClient.cs` produced:

- 3 × `CS0168: The variable 'ex' is declared but never used` (unused catch variables in `TimeoutException`, `TaskCanceledException`, `HttpRequestException` catch clauses on the retry path)
- 1 × `CA1513: Use 'ObjectDisposedException.ThrowIf' instead of explicitly throwing a new exception instance`

**Root Cause:**
In the retry paths, we intentionally suppressed exceptions to loop again, but we still named the catch variable `ex`. Only the final (non-retrying) branches actually used `ex.Message`. Additionally, we used the older pattern `if (_disposed) throw new ObjectDisposedException(nameof(RemoteClient));` instead of the modern .NET 8 static helper.

**Risk:**
The WorkGrid quality baseline is **zero warnings**. Any tolerated warning would breach the acceptance criteria in Section 21 of the brief.

**Mitigation (Block 4b):**

1. Removed the variable name from catch clauses that did not use it:
   - `catch (TimeoutException)` instead of `catch (TimeoutException ex)`
   - `catch (TaskCanceledException)` instead of `catch (TaskCanceledException ex)`
2. Kept the variable named `ex` **only** in branches that actually reference `ex.Message` (`HttpRequestException` and generic `Exception`).
3. Replaced the disposed-check with `ObjectDisposedException.ThrowIf(_disposed, typeof(RemoteClient));`.

**Verification:**
Immediate rebuild produced `0 Warning(s), 0 Error(s)`.

---

### 6.5 Problem: xUnit Analyzer Warning `xUnit1031` in Test Suite

**Symptom:**
```
xUnit1031: Test methods should not use blocking task operations, as they can cause deadlocks.
```

**Cause:**
The test `UpdateEndpoint_ResetsStateToUnknown` used `.Result` to block on the initial async call in a synchronous `[Fact]`.

**Risk:**
Blocking on `.Result` inside a test can deadlock and — more importantly — violated the zero-warning baseline.

**Mitigation (Block 6b):**

1. Converted the test method to `async Task`.
2. Replaced `client.ExecuteAsync(...).Result` with `await client.ExecuteAsync(...)`.

**Verification:**
Rebuild produced `0 Warning(s), 0 Error(s)`. All 105 tests passed.

### 6.6 Design Consideration: Distinguishing `TaskCanceledException` from True Cancellation

**Challenge:**
`HttpClient` throws `TaskCanceledException` for **both** timeout and user-initiated cancellation. Naïvely mapping this to a single error kind would violate the brief's requirement that error kinds be distinguishable.

**Mitigation:**
The `catch` clauses in `RemoteClient.ExecuteAsync(...)` are ordered and filtered so that:

1. `catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)` is matched **first** and maps to `RemoteErrorKind.Cancelled`.
2. `catch (TaskCanceledException)` (without token cancellation) maps to `RemoteErrorKind.Timeout`.

This preserves the ability of the eventual caller to distinguish "user pressed back" from "server did not respond."

**Verification:**
Two dedicated tests cover this — `ExecuteAsync_WhenCancellationRequested_ReturnsCancelledState` and `ExecuteAsync_OnTimeout_ReportsTimeoutAndDisconnected`.

---

### 6.7 Design Consideration: Which HTTP Status Codes Are Transient?

**Challenge:**
Blindly retrying every non-2xx response would violate the brief's warning against aggressive retry loops. Retrying `401 Unauthorized`, `404 Not Found`, or `400 Bad Request` is semantically wrong — these are not transient.

**Mitigation:**
Retry logic in `RemoteClient` retries **only** on:

- HTTP 5xx (server-side errors, presumed transient)
- `HttpRequestException` (connection failed, DNS failed, socket reset)
- `TimeoutException` and `TaskCanceledException` (without token cancellation)

Non-transient failures (`401`, `403`, `404`, etc.) return **immediately** without retry. The retry budget is hard-capped at **2 retries** (3 total attempts) with a fixed 200 ms delay. No exponential backoff, no infinite loops.

**Verification:**
- `ExecuteAsync_OnTransientErrorThenSuccess_RecoversAndSucceeds` — proves 5xx retry works.
- `ExecuteAsync_OnRepeatedTransientErrors_ExhaustsRetriesAndReportsDisconnected` — proves retry budget is bounded.
- `ExecuteAsync_On401Unauthorized_ReturnsUnauthorizedFailureAndConnectedState` — proves auth failures are **not** retried.
- `ExecuteAsync_On404NotFound_ReturnsHttpFailure` — proves 4xx failures are **not** retried.

---

### 6.8 Design Consideration: Backward Compatibility of `AddInfrastructure(...)` Signature

**Challenge:**
The existing composition root in `MauiProgram.cs` calls `services.AddInfrastructure(dbPath)`. Changing this method signature would either (a) force a change in `MauiProgram.cs`, or (b) break the App build.

The brief explicitly forbids casual changes to the composition root and forbids rewriting the App layer.

**Mitigation:**
Added the new parameter as **optional with a default value**:

```csharp
public static IServiceCollection AddInfrastructure(
    this IServiceCollection services,
    string databasePath,
    RemoteEndpoint? remoteEndpoint = null)
```

The default endpoint (`https://localhost:5001`) is applied inside the method when the caller passes nothing. This means:

- Existing `MauiProgram.cs` compiles unmodified.
- Future callers (or a later sprint) can supply a real endpoint without further API changes.
- Tests can supply a test endpoint if needed.

**Verification:**
`MauiProgram.cs` was untouched, and both the desktop build and the Android build (`net8.0-android`) succeeded with zero warnings.

## 11. Handoff Notes for Next Sprint

The remote boundary is **ready but idle**. To make future sprint work smoother, note:

1. **No caller yet exists** for `IRemoteClient`. The boundary is fully registered in DI but is not injected into any ViewModel or service. This is intentional per the S4.1 scope.
2. **Endpoint is defaulted** to `https://localhost:5001`. A future sprint should introduce a proper configuration source (e.g. an `appsettings.json` mechanism appropriate for MAUI, or a settings UI) rather than the hardcoded default. This was deliberately deferred as building an elaborate configuration system was outside sprint scope.
3. **Authentication is not integrated.** The abstraction is prepared for authenticated requests (the caller passes an `HttpRequestMessage` via `HttpClient` and can set headers), but there is no token injection pipeline yet. A later sprint will need to introduce a token acquisition/renewal flow. The design does not require any refactor to add this.
4. **State observability** is per-instance via the `StateChanged` event. If a global connectivity indicator UI is needed later, it can subscribe directly since `IRemoteClient` is a singleton.
5. **`WorkGrid.Api`** was not extended in this sprint. Section 5 of the brief was explicit that S4.1 is not the API implementation sprint.
