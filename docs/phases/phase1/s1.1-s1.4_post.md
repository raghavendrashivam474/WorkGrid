**Prepared for:** Senior Developer / Technical Lead

## 1. Executive Summary

Phase 1 successfully transformed WorkGrid from an architectural scaffold (`v0.0`) into a functional, local-first Android application (`v1.0`). Over four sprints (S1.1 through S1.4), we introduced MAUI Shell navigation, EF Core + SQLite persistence, full Employee CRUD, full Asset CRUD with lifecycle state management, and business-rule-guarded deletion — all operating entirely offline on a single device.

## 2. Sprint-by-Sprint Breakdown

---

### 2.1 S1.1 — MAUI UI Foundation (`vS1.1`)

**Objective:** Replace the single-screen Phase 0 demonstration with a navigable multi-screen application shell.

#### What Was Done

- Created `AppShell.xaml` / `AppShell.xaml.cs` with flyout navigation to three tabs: **Home**, **Employees**, **Assets**.
- Registered detail page routes (`employee-detail`, `asset-detail`) in the Shell constructor for programmatic navigation.
- Updated `App.xaml.cs` to set `MainPage = appShell` instead of the Phase 0 `MainPage`.
- Scaffolded six new pages with code-behind: `HomePage`, `EmployeeListPage`, `EmployeeDetailPage`, `AssetListPage`, `AssetDetailPage` (plus the preserved `MainPage`).
- Created corresponding ViewModels inheriting from the existing `ViewModelBase` — no external MVVM frameworks introduced.
- Wired all pages and ViewModels through explicit `AddTransient<T>()` registrations in `MauiProgram.cs`.

#### Problems Encountered & Resolutions

| # | Problem | Resolution |
|---|---|---|
| 1 | **No AppShell existed in Phase 0.** It was intentionally removed because there was only one screen. Reintroducing it meant changing the application entry point, which risked breaking the existing DI chain. | We preserved `MainPage.xaml` and `MainViewModel.cs` entirely. The `App.xaml.cs` constructor parameter was changed from `MainPage` to `AppShell`. The `MainPage` registration remains in DI for backward compatibility. |
| 2 | **Detail pages referenced in route registration didn't exist yet** when `AppShell.xaml.cs` was first created. | Routes were forward-declared in `Routing.RegisterRoute()` pointing to the detail page types. The pages were scaffolded as empty shells in the same sprint, so the routes resolved correctly at build time. |
| 3 | **`x:DataType` binding in XAML required cross-assembly references** to `WorkGrid.Domain` for entity types used in `CollectionView` templates. | Added explicit `xmlns:entities="clr-namespace:WorkGrid.Domain.Entities;assembly=WorkGrid.Domain"` declarations in the XAML files. |

#### Acceptance Criteria Status: ✅ All Met

---

### 2.2 S1.2 — Local Persistence (`vS1.2`)

**Objective:** Introduce durable local storage using EF Core 8 + SQLite, entirely within the Infrastructure layer.

#### What Was Done

- Added `Microsoft.EntityFrameworkCore.Sqlite 8.0.11` to `WorkGrid.Infrastructure.csproj` only. Verified Domain project remains at zero external packages.
- Created `WorkGridDbContext` with `DbSet<Employee>`, `DbSet<Asset>`, `DbSet<Assignment>`.
- Created explicit Fluent API configurations (`EmployeeConfiguration`, `AssetConfiguration`, `AssignmentConfiguration`) handling: primary keys, unique indexes on `EmployeeCode`/`AssetTag`, string max lengths, nullable fields, and enum-to-int conversions.
- Defined three repository contracts in `WorkGrid.Domain/Contracts/`: `IEmployeeRepository`, `IAssetRepository`, `IAssignmentRepository` — all explicit, no generic `IRepository<T>`.
- Implemented all three repositories in `WorkGrid.Infrastructure/Repositories/`.
- Created `ServiceCollectionExtensions.AddInfrastructure(string databasePath)` in `WorkGrid.Infrastructure/DependencyInjection/`.
- Updated `MauiProgram.cs` to resolve the database path via `FileSystem.AppDataDirectory` and call `dbContext.Database.EnsureCreated()` at startup.
- Wrote 5 integration tests using in-memory SQLite connections covering: employee CRUD, asset lifecycle persistence, assignment active-check queries, and return lifecycle.

#### Problems Encountered & Resolutions

| # | Problem | Resolution |
|---|---|---|
| 1 | **Domain entities use `private set` on all properties and parameterized constructors.** This is a deliberate Phase 0 design choice to enforce invariants. EF Core needs to materialize entities from the database. | EF Core 8 supports constructor binding natively when constructor parameter names match property names (case-insensitive). Since our entities follow this convention (`id` → `Id`, `name` → `Name`, etc.), no backing field configuration was needed. We verified this with integration tests. |
| 2 | **`ExistsByCodeAsync` and `ExistsByTagAsync` triggered CA1304/CA1311/CA1862 analyzer warnings** about culture-sensitive `string.ToUpper()` calls. | These are warnings, not errors. The domain already normalizes `EmployeeCode` via `.Trim()` and `AssetTag` via `.Trim().ToUpperInvariant()` at construction time. The repository-level comparison uses `.ToUpper()` for query-side normalization. This was documented as acceptable technical debt — a future sprint can replace with `StringComparison.OrdinalIgnoreCase` if needed. |
| 3 | **Database file location on Android.** Hardcoding a Windows path would break on-device. | Used `Path.Combine(FileSystem.AppDataDirectory, "workgrid.db3")` which resolves to the correct platform-specific application data directory on both Android and Windows. |
| 4 | **`EnsureCreated()` vs. Migrations.** The brief explicitly warned against introducing complicated migration orchestration. | We used `EnsureCreated()` which creates the schema from the model on first run. This is appropriate for a local-first mobile app where the database is device-local and can be recreated. If schema evolution is needed in future phases, EF migrations can be layered on top. |

#### Acceptance Criteria Status: ✅ All Met

---

### 2.3 S1.3 — Employee Management (`vS1.3`)

**Objective:** Deliver the first complete vertical slice — Employee list, create, edit, and delete — wired to real SQLite persistence.

#### What Was Done

- Rewrote `EmployeeListViewModel` to inject `IEmployeeRepository`, load employees into an `ObservableCollection<Employee>`, and expose `IsLoading`, `IsEmpty`, `StatusMessage` states.
- Rewrote `EmployeeListPage.xaml` with `RefreshView` + `CollectionView` displaying Name, Code, Email, and Department.
- Rewrote `EmployeeDetailViewModel` to support both **Create** (empty `id` query param) and **Edit** (valid GUID) modes. Injected both `IEmployeeRepository` and `IAssignmentRepository`.
- **Delete guard:** Before deletion, queries `IAssignmentRepository.HasActiveAssignmentsForEmployeeAsync()`. If active assignments exist, deletion is blocked with a user-facing error message.
- Domain invariants are respected: new employees use the `Employee` constructor; edits use `UpdateDetails()`. `DomainValidationException` is caught and displayed.
- Created `InverseBoolConverter` and `IsNotNullOrEmptyConverter` in `WorkGrid.App/Converters/` and registered them globally in `App.xaml`.
- Added `SecondaryButtonStyle` to `App.xaml` resources.

#### Problems Encountered & Resolutions

| # | Problem | Resolution |
|---|---|---|
| 1 | **`EmployeeDetailPage.xaml` referenced `{StaticResource SecondaryButtonStyle}` and two converters that didn't exist.** The Phase 0 `App.xaml` only merged `Colors.xaml` and `Styles.xaml`. | Created both converters as simple `IValueConverter` implementations. Added `SecondaryButtonStyle` and converter resource declarations to `App.xaml`. This was a deliberate choice to keep converters in-app rather than pulling in a third-party toolkit. |
| 2 | **Employee deletion business rule was undefined in Phase 0.** The domain model had no concept of "can this employee be deleted?" — it was purely a persistence concern. | Rather than silently allowing destructive deletes, we implemented a guard check at the ViewModel level using `IAssignmentRepository.HasActiveAssignmentsForEmployeeAsync()`. This decision was documented in **ADR-0002**. The repository contract was already designed with this method in S1.2, anticipating this exact need. |
| 3 | **`OnAppearing` lifecycle for data loading.** The list page needed to reload data when navigating back from the detail page (e.g., after creating a new employee). | Overrode `OnAppearing()` in `EmployeeListPage.xaml.cs` to call `await _viewModel.LoadEmployeesAsync()`. This ensures the list refreshes every time the user returns to it. |
| 4 | **Uniqueness check on `EmployeeCode`.** The domain constructor doesn't check for duplicate codes — it only validates format. | Added `ExistsByCodeAsync()` check in the ViewModel's save flow before constructing the domain entity. If the code already exists, a user-friendly error is shown. This keeps the domain pure (it doesn't know about databases) while enforcing uniqueness at the application layer. |

#### Acceptance Criteria Status: ✅ All Met

### 2.4 S1.4 — Asset Management (`vS1.4`)

**Objective:** Deliver the Asset vertical slice with full lifecycle state management and assignment-ready persistence.

#### What Was Done

- **Domain enhancement:** Added `UpdateDetails(string name, string? assetType, string? serialNumber)` method to `Asset.cs` with invariant validation. The Phase 0 `Asset` entity only had lifecycle transition methods but no way to update descriptive fields.
- Added 5 new domain unit tests for `UpdateDetails` (valid data, null/empty/whitespace name rejection).
- Rewrote `AssetListViewModel` and `AssetListPage.xaml` following the same pattern as Employee (RefreshView, CollectionView, empty/loading states).
- Rewrote `AssetDetailViewModel` with:
  - Create/Edit mode support via `id` query parameter.
  - **Lifecycle transition commands:** `MarkAvailableCommand`, `MarkMaintenanceCommand`, `RetireCommand` — each invokes the corresponding domain method (`MarkAvailable()`, `MarkMaintenance()`, `Retire()`), catching `DomainValidationException` for invalid transitions.
  - **Retired terminal state:** `IsRetired` boolean property bound to UI visibility. When an asset is retired, transition buttons are hidden and a "terminal state" message is shown.
  - **Delete guard:** Same pattern as Employee — checks `HasActiveAssignmentsForAssetAsync()` before allowing deletion.
- Rewrote `AssetDetailPage.xaml` with a status display frame, transition buttons, form inputs, and error banner.

#### Problems Encountered & Resolutions

| # | Problem | Resolution |
|---|---|---|
| 1 | **`Asset` entity lacked an `UpdateDetails` method.** Unlike `Employee` which had `UpdateDetails` from Phase 0, `Asset` only had state transition methods. Direct property mutation was impossible due to `private set`. | Added `UpdateDetails(string name, string? assetType, string? serialNumber)` to the domain entity with proper validation (name cannot be null/whitespace). This preserves the invariant that `AssetTag` is immutable after creation (set via constructor, normalized to uppercase). Corresponding unit tests were added. |
| 2 | **Asset lifecycle state machine needed to be exposed in the UI without bypassing domain rules.** A naive approach would be a status dropdown that sets `Status` directly. | Instead of a dropdown, we exposed discrete command buttons (`MarkAvailable`, `MarkMaintenance`, `Retire`) that invoke the domain's own transition methods. The domain methods already enforce the rules (e.g., retired assets cannot transition). The ViewModel catches `DomainValidationException` and displays the error. This means the UI cannot create an invalid state even if the developer makes a mistake in the XAML. |
| 3 | **Retired state is terminal but the UI needed to communicate this clearly.** Simply disabling buttons could confuse users. | Added an `IsRetired` property to the ViewModel that updates whenever `Status` changes. In the XAML, transition buttons are hidden when `IsRetired` is true, and a descriptive label ("This asset is retired (terminal state)") is shown instead. |
| 4 | **Asset tag immutability in edit mode.** The domain normalizes `AssetTag` to uppercase in the constructor. Allowing tag edits in the detail form could violate this. | The `AssetTag` entry field is disabled in edit mode (`IsEnabled="{Binding IsEditMode, Converter={StaticResource InverseBoolConverter}}"`). The `UpdateDetails` method intentionally does not accept a tag parameter. Tags are set once at creation. |

#### Acceptance Criteria Status: ✅ All Met

## 3. Architectural Decisions Made

| ADR | Decision | Rationale |
|---|---|---|
| **ADR-0001** | EF Core 8 + SQLite in Infrastructure only | Local-first requirement; Domain must remain framework-independent; EF Core provides compile-time query safety |
| **ADR-0002** | Active assignment guard rules for deletion | Prevents orphaned allocations; preserves audit integrity; enforced at ViewModel level using repository queries |
