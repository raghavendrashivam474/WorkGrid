## 1. Executive Summary

AV1.10 and AV1.11 represent the final two sprints of the Android v1.0 Product Hardening track. The objective was not to introduce new functionality or refactor existing architecture, but to **prove that the WorkGrid application — as hardened across AV1.1 through AV1.9 — can be packaged, signed, installed, and operated as a production Android application on physical hardware.**

Both sprints completed successfully. The final release artifact (`WorkGrid-v1.0.0-Release.apk`, package `com.workgrid.app`, SHA-256 `3152C08F...`) has been generated, installed on a physical Android device, and validated across all core product workflows. All 121 automated tests pass in both Debug and Release configurations with zero errors and zero .NET-level warnings.

One P1 defect was discovered and resolved during AV1.11 regression testing (Assignment creation dropdown population failure). The fix was minimal, isolated to a single file, and did not alter any architectural boundary.

### 2.2 Problems Faced & Mitigations

#### Problem 1: Template Metadata Leakage

**Observation:** The `ApplicationId` was still set to `com.companyname.workgrid.app` — a .NET MAUI template placeholder that would be rejected by Google Play Store and is inappropriate for any production distribution.

**Mitigation:** Updated `ApplicationId` to `com.workgrid.app` and `ApplicationTitle` to `WorkGrid` in a single atomic commit. No other files required changes since MAUI propagates these values into the manifest at build time.

**Risk Assessment:** Low. This is a metadata-only change with no runtime behavior impact. The package identifier change means the new APK cannot be installed as an update over the old debug package (different signing identity + different package name), requiring a clean install on test devices.

#### Problem 2: JAVAC Obsolete Source/Target Warnings

**Observation:** During Release compilation, three JAVAC warnings appeared:
```
JAVAC : warning : [options] source value 8 is obsolete and will be removed in a future release
JAVAC : warning : [options] target value 8 is obsolete and will be removed in a future release
JAVAC : warning : [options] To suppress warnings about obsolete options, use -Xlint:-options
```

**Analysis:** These originate from the Android SDK build tools (version 34.0.0) invoking `javac` with Java 8 source/target compatibility against JDK 21. This is a toolchain-level configuration within the MAUI Android SDK targets, not within our project code.

**Mitigation:** No action taken. These are informational warnings from the Java compiler about future deprecation, not errors or correctness issues. The generated bytecode is valid and functional. Suppressing them would require modifying MAUI SDK targets or passing custom JAVAC flags, which falls outside the scope of this sprint and could introduce toolchain fragility.

**Decision:** Classified as P3 (cosmetic). Documented for future toolchain upgrade cycles.

#### Problem 3: No ADB-Connected Device During Initial Inspection

**Observation:** Running `adb devices -l` returned an empty device list during Block 6 inspection.

**Mitigation:** The physical Android device was connected and the APK was sideloaded manually by the developer for on-device validation. ADB connectivity was not required for the build/publish pipeline itself.

**Note for future sprints:** For CI/CD automation, an emulator image or persistent ADB-connected device will be needed for automated device-level testing.

#### 3.1.4 P1 Defect Discovery & Resolution: Assignment Dropdown Population Failure

**This was the most significant finding of AV1.11.**

**Symptom:** When navigating to the Assignment creation screen (Assignments → `+` button), both the "Assign to Employee" and "Select Available Asset" Picker controls were empty. No employees or assets appeared in the dropdowns, despite records existing in the local database. The Employee and Asset list pages themselves displayed data correctly.

**Root Cause Analysis:**

The `AssignmentDetailViewModel` uses a `[QueryProperty(nameof(IdString), "id")]` attribute to receive navigation parameters. The `IdString` setter contains the branching logic:

```csharp
public string? IdString
{
    set
    {
        if (Guid.TryParse(value, out var parsedId) && parsedId != Guid.Empty)
        {
            // Edit mode: load existing assignment
            MainThread.BeginInvokeOnMainThread(async () => await LoadAssignmentAsync());
        }
        else
        {
            // Create mode: load selection sources
            MainThread.BeginInvokeOnMainThread(async () => await LoadSelectionSourcesAsync());
        }
    }
}
```

When navigating to **edit** an existing assignment (`assignment-detail?id=<guid>`), Shell passes the query parameter and the setter fires correctly.

However, when navigating to **create** a new assignment (`assignment-detail` with no query parameter), **Shell never invokes the `IdString` setter** because there is no `id` parameter in the navigation URI. As a result, `LoadSelectionSourcesAsync()` was never called, and the `Employees` and `AvailableAssets` `ObservableCollection` properties remained empty.

This is a known .NET MAUI Shell behavior: `[QueryProperty]` setters are only invoked when the corresponding query parameter is present in the navigation URI. Parameterless navigation does not trigger them.

**Comparison with other Detail pages:** `EmployeeDetailViewModel` and `AssetDetailViewModel` exhibit the same pattern but do not suffer from this issue because their Create mode does not require loading external data sources — they simply present empty input forms. The Assignment Create form is unique in requiring pre-populated Picker collections from other repositories.

**Fix Applied:**

Added an `OnAppearing` lifecycle override to `AssignmentDetailPage.xaml.cs`:

```csharp
protected override async void OnAppearing()
{
    base.OnAppearing();
    if (!_viewModel.IsEditMode)
    {
        await _viewModel.LoadSelectionSourcesAsync();
    }
}
```

This ensures that when the page appears in Create mode (regardless of whether the QueryProperty setter fired), the employee and asset collections are populated from the local database.

**Files Changed:** 1 file — `src/WorkGrid.App/Views/Assignments/AssignmentDetailPage.xaml.cs`
**Lines Changed:** +12, -1
**Architectural Impact:** None. This is a page lifecycle correction, not an architectural change.

**Verification:** After applying the fix, the Release APK was rebuilt, reinstalled on the physical device, and the Assignment creation workflow was retested. Both dropdowns populated correctly with existing employees and available assets.

## 5. Known Limitations & Future Work

The following items are explicitly **not** included in Android v1.0 and are deferred to future architectural phases:

1. **Remote Synchronization:** The API exists and is functional, but the Android client operates in local-first mode only. Synchronization, conflict resolution, and offline queue reconciliation are designated for **Phase 5 — Synchronization** as a deliberately designed architectural effort.

2. **Release Keystore Provisioning:** The current Release APK is signed with the MAUI auto-generated debug keystore. For Google Play Store distribution, a dedicated release keystore with secure credential management (e.g., CI/CD secret injection) will need to be provisioned.

3. **AOT Compilation:** Not enabled for this release. Can be evaluated in future performance optimization sprints.

4. **Automated Device Testing:** No CI/CD device testing pipeline exists. Physical device validation was performed manually. Future sprints should establish Appium or similar automated UI testing infrastructure.

5. **JAVAC Source/Target Warnings:** Cosmetic toolchain warnings from Java 8 compatibility mode against JDK 21. Will resolve naturally with future Android SDK / MAUI workload updates.
